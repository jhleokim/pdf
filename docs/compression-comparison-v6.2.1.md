# Stirling PDF와 PDF Studio 용량 최적화 비교

검토일: 2026-09-16. Stirling PDF의 공개 최신 릴리스 v2.14.3과 PDF Studio v6.2.1 소스를 비교했습니다. **동일 문서로 두 프로그램의 압축률·속도를 측정한 벤치마크는 아닙니다.** 이번 버전에서는 자동 적용 기본값을 변경했으며 압축 엔진 자체를 교체하지 않았습니다.

## 알고리즘 차이

| 항목 | Stirling PDF v2.14.3 | PDF Studio v6.2.1 |
|---|---|---|
| 처리 방식 | 서버의 QPDF·Ghostscript와 Java/PDFBox 조합. 설치된 도구와 압축 강도에 따라 경로가 달라짐 | 브라우저 Canvas·pdf-lib로 PDF 내부 이미지 객체를 선별 처리 |
| 이미지 압축 | PDFBox 재압축, QPDF 이미지 최적화, 강한 설정에서 Ghostscript 해상도 축소 | 이미지 긴 변 제한 + JPEG 품질. 선택한 흑백 변환은 1비트 Flate 저장 |
| PDF 구조 | QPDF로 스트림 재압축·객체 스트림 생성 등 구조 최적화 | pdf-lib 객체 스트림 저장과 동일 이미지 중복 제거. 별도의 QPDF 수준 최적화 단계는 없음 |
| 지원 범위 | 여러 네이티브 도구의 디코더와 PDF 재작성 기능 활용 | 안전하게 처리 가능한 8비트 RGB/Gray의 JPEG·Flate·원시 이미지 중심. 특수 색 공간·마스크·일부 압축 형식·16MP 초과 이미지는 유지 |
| 용량 목표 | 압축 강도 1–9 또는 목표 용량. 목표에 못 미치면 강도를 높여 재시도 | 선택한 해상도·품질로 한 번 처리. 목표 용량을 향한 자동 탐색은 없음 |
| 텍스트 유지 | 일반 압축은 PDF 내용을 재작성하는 경로이며 전체 페이지 이미지 변환이 필수는 아님 | 기본 ‘텍스트 유지’는 이미지 객체만 교체. 전체 페이지 이미지 변환은 별도 선택 |
| 작은 결과 선택 | 원본보다 커진 결과를 원본으로 되돌리는 검사 존재 | 이미지마다 크기 비교. 압축만 한 결과가 더 크면 기존 편집본 유지. 마스킹에서는 삭제 전 원본을 반환하지 않음 |

Stirling의 실제 경로는 [v2.14.3 압축 컨트롤러](https://github.com/Stirling-Tools/Stirling-PDF/blob/v2.14.3/app/core/src/main/java/stirling/software/SPDF/controller/api/misc/CompressController.java)를 기준으로 확인했습니다. 강도·목표 용량·선형화·흑백 등의 사용자 옵션은 [공식 압축 문서](https://docs.stirlingpdf.com/Functionality/Compress/)에 설명되어 있습니다.

우리 구현의 근거: [이미지 처리와 중복 제거](../src/pro-engine.js), [출력 크기 비교](../src/pro-result.js), [보정·OCR·저장 파이프라인](../src/pro-pipeline.js), [이미지 압축 가능 여부 분석](../src/compression-diagnosis.js).

## 평가

**Stirling은 압축할 수 있는 대상과 방법의 범위가 더 넓습니다.** 우리 코드가 건너뛰는 이미지나 구조상 불필요한 데이터가 많은 문서에서는 유리할 가능성이 있습니다. 강한 설정에서 해상도와 JPEG 품질을 낮추는 효과도 크므로, 더 작은 파일이 곧 같은 화질에서 더 우수한 알고리즘을 뜻하지는 않습니다.

PDF Studio는 설치 없는 단일 HTML과 기기 내부 처리를 유지합니다. 200명이 각각 자기 브라우저에서 처리하므로 중앙 압축 서버의 작업 대기열을 운영할 필요가 없습니다. 대신 브라우저 메모리와 지원 형식에 제약을 둡니다. Stirling도 사내 서버나 로컬 환경에서 운영할 수 있으므로 외부 클라우드 업로드가 필수인 도구로 해석하면 안 됩니다. 서버 방식에는 프로세스 동시 실행과 자원 관리가 필요합니다. [Stirling 프로세스 제한 문서](https://docs.stirlingpdf.com/Configuration/Operations/Process-Limits/)

## 우리 프로젝트의 개선 우선순위

1. **실제 배치 크기에 맞는 해상도 계산.** 지금은 긴 변 2,400px 같은 고정 기준입니다. 페이지에 작게 들어간 큰 이미지는 더 줄이고, 글자가 많은 전면 스캔은 필요한 해상도를 남기는 방식이 적합합니다. 같은 이미지가 여러 크기로 재사용되면 가장 높은 필요 해상도를 기준으로 해야 합니다.
2. **원본에서 제한된 후보만 비교.** 최대 2–3개 해상도·품질 후보를 원본에서 만들어 비교하는 목표 용량 옵션을 검토합니다. 이미 압축한 결과를 반복 압축하지 않고, 취소와 메모리 상한을 유지해야 합니다. 처리 시간이 늘어나므로 기본 자동 실행에는 넣지 않습니다.
3. **기존 MuPDF 활용 가능성 검증.** 이미 개인정보 제거에 포함한 엔진으로 객체·스트림 정리를 확장할 수 있는지 확인합니다. 새 네이티브 엔진을 추가하기 전에 검색 텍스트, 글꼴, 회전·재단 좌표와 파일 크기가 유지되는지 검증해야 합니다.

지원 형식을 무작정 늘리거나 계약서를 자동 흑백화하는 방식은 우선하지 않습니다. 현재의 압축 제외 사유 표시, 검색 텍스트 유지, 작은 결과 선택을 보존합니다. 개선 효과는 같은 계약서에서 파일 크기·소요 시간·화면/인쇄 가독성·텍스트 추출 결과를 함께 측정해야 판단할 수 있습니다.
