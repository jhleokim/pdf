# v6.4.6 — 대용량 문서 안정성 점검

검토일: 2026-09-19. 불러오기·편집/이력·썸네일·OCR·교정·마스킹·저장 경로를 분담 검토하고 서로 교차 검토했다. 대용량 처리를 무조건 보장하는 릴리스는 아니다. 아래의 실제 검증 범위와 남은 한계를 구분한다.

## 수정 사항

- 불러오기를 파일 단위로 확정한다. 중간 페이지가 손상됐거나 취소된 파일은 일부만 문서에 섞이지 않는다. 이전에 완료한 파일과 기존 편집은 유지한다. 중복 불러오기와 다른 작업의 취소 버튼을 덮어쓰는 경쟁 조건을 막고, Pro 작업 취소 후에도 새 불러오기를 취소할 수 있다.
- 마스킹 120초·이미지 배치 분석 30초 제한을 **전체 문서 경과 시간** 대신 **새 진행 응답이 없는 시간**으로 적용한다. 진행 수치가 정상적으로 증가하는 작업은 계속한다. 초기화 실패·취소·오래된 Worker 응답의 처리도 보완했다.
- PDF.js 페이지 렌더링 및 텍스트 비교가 끝나면 페이지 자원을 정리한다. 네이티브 엔진은 작업 후 내부 캐시를 비운다. 임시 PDF 버퍼 전달 시 불필요한 전체 복사를 줄인다.
- 이미지 변환이 필요 없는 저장은 이미지별 예약 작업과 마스크 그래프 생성을 생략한다. 중복 검사와 교체된 이미지 스트림의 참조 보관을 줄인다.
- OCR 페이지 준비 중 문서 전체의 승인된 OCR 데이터를 매번 재구성하지 않는다. 기존 텍스트가 있는 페이지를 건너뛰는 동안에도 취소·진행·이어하기가 작동한다. 교정 입력 시 다른 모든 페이지의 단어를 매번 순회하지 않는다.
- 삭제한 페이지의 OCR 결과가 남은 페이지의 교정/저장을 막지 않도록 한다. 현재 문서와 undo/redo 어디에서도 참조하지 않는 원본 PDF·OCR 결과를 해제한다. 이력의 비활성 원본 PDF 예산은 128MiB이며 가장 최근 작업 하나의 되돌리기는 유지한다. 이는 전체 앱 메모리 상한이 아니다.
- 썸네일 대기열·페이지 조회를 Set/WeakMap으로 관리한다. 스크롤·삭제·undo 중 늦게 완료된 썸네일이 다른 페이지에 게시되지 않도록 한다. 화면 주변 페이지에만 이동 애니메이션을 적용한다.
- 페이지 복제는 준비가 끝난 뒤 확정하고 원본 PDF 바이트를 공유한다. 복제, 빈 페이지 추가, Pro→Basic 전환은 미리보기 오류가 나더라도 완료한 편집을 되돌릴 수 있다.

## 검증 환경과 재현

Windows, 64GB RAM, Chromium 기반 앱 브라우저. 합성 문서만 사용했으며 실제 회사 문서를 외부 OCR로 전송하지 않았다. 파일 내용·기기 성능에 따라 결과가 달라진다. 사용자에게 예전에 전달받은 대용량 PDF는 현재 파일 경로에 없어 이번 실행에 사용하지 못했다.

```sh
node scripts/build.mjs
node --test --test-concurrency=1 tests/*.test.cjs
node tests/create-large-workflow.cjs
python tests/serve-local.py
```

브라우저에서 `/tests/fixtures/large-workflow.html?kind=scan&count=212` 또는 `?kind=text&count=1000`을 연다. `--baseline`은 현재 빌드를 별도 이름으로 복사하므로 비교할 이전 버전에서 먼저 실행해야 한다. 페이지 수, 출력 PDF, 렌더 캐시, 메인 스레드 지연과 JS heap 표본을 보고한다. JS heap은 탭/프로세스 전체 메모리나 최고 사용량을 의미하지 않는다.

## 실제 결과

자동 테스트 **417개 통과**. 300페이지 OCR 순차 처리·취소/재개, 212페이지 중 90페이지 실패 후 재시도, 24만 단어의 반복 검사 비용, 501페이지 교정 입력 비용을 포함한다. 이 OCR 배치 테스트의 엔진·클라우드 응답은 모의 응답이다.

실제 MuPDF로 400페이지 중 58페이지를 마스킹하여 비대상 검색 텍스트 보존을 검사했다. 작업 시간 제한·정지·잘못된 진행 메시지·초기화 취소는 가상 시계와 Worker로 별도 검증했다.

최종 브라우저 측정 결과는 아래 표에 기록한다.

| 문서 | 불러오기 | 전체 Basic 저장 | 결과 |
|---|---:|---:|---|
| 1,000페이지 단순 텍스트, 0.21MiB | 3.89초 | 18.79초 | 완료, 선택 저장은 정확히 3페이지 |
| 212페이지 합성 스캔, 90.49MiB | 1.01초 | 3.87초 | 완료, 선택 저장은 1.28MiB·3페이지 |

212페이지 스캔의 Pro OCR 포함 저장은 **7.39초**, 출력은 **90.53MiB**였다. v6.4.5 동일 합성 문서의 한 번 측정은 10.80초였다. 이 단계 종료 시 JS heap 표본은 934→757MiB였지만 GC 시점에 영향을 받으므로 최고 메모리 감소율로 해석하지 않는다. 전체 OCR 클라이언트 반복은 63.10초, 완료 결과 재사용은 3.08초였으며 **Google 응답은 모의 처리했다. 이 시간은 실제 Google 인식 속도가 아니다.** 엔진 서버 지연·인터넷 장애·조직 동시 접속은 실측하지 않았다. 페이지별 실제 렌더링·JPEG 생성과 출력 PDF 저장을 수행했다.

미리보기 캔버스 캐시는 시험에서 22~24개였다. 대용량 테스트 두 개 모두 외부 문서/API 전송 없이 완료했다. 짧은 벤치마크 반복만으로 모든 PDF의 속도 개선을 보장하지 않는다.

실제 로컬 Paddle/Tesseract에서 한글·영문·숫자 인식에 성공했다. 외부 HTTP를 차단한 Tesseract 검사는 검색 가능한 PDF 저장, 원본 렌더 픽셀 보존, 회전/재단/UserUnit 도장 배치, 압축 후 OCR 유지까지 5개 검사를 통과했다.

브라우저 회귀 검사: 페이지 메뉴 데스크톱/390px 각 14개, 이동 애니메이션 데스크톱/390px 각 8개, 선택 저장 9개, 형광펜 좌표 6개, 전체 미리보기 10개, 되돌리기 18개 통과. 단독 HTML을 로컬 HTTP로 제공하고 외부 연결을 차단한 Basic/Pro 연동 12개 검사도 통과했다. 웹 자산 지연 로딩에 맞지 않았던 일부 테스트 생성기의 CSP와 예전 버전 고정 경로도 정비했다.

## 남은 한계와 우선순위

1. **1,000페이지 일괄 편집에는 멈춤이 남는다.** 전체 회전+되돌리기에서 메인 스레드 지연이 약 1.46초였다. 카드 전체 DOM 재생성을 화면에 필요한 카드만 재사용하는 방식으로 바꾸는 후속 작업이 필요하다. 작은 문서의 드래그/키보드/선택 정확성을 유지해야 하므로 이번에 전면 가상화하지 않았다.
2. **저장은 문서 전체를 메모리에 보관한다.** pdf-lib 및 네이티브 변환, 검색 텍스트 검증에 전체 바이트와 객체가 필요하다. 수백 MB~GB 문서, 고해상도 스캔, 저메모리 모바일에서는 중단 가능성이 남는다. 스트리밍 저장 또는 파일 기반 엔진은 별도 구조 변경이 필요하다.
3. **Google Vision은 조직 동시 사용 병목이 있다.** 현재 Worker 설정은 `15회/60초`, 요청들이 `pdf-vision-ocr` 키를 공유한다. 위치별 제한 동작과 Google 프로젝트 할당량도 영향을 준다. 200명 동시 Vision 사용을 검증한 것이 아니며 현재 설정으로 이를 보장할 수 없다. 서버 인증·사용자별 공정한 요청 대기열과 조직 예산/할당량 정책이 필요하다. 이번에 호출 한도를 임의로 올리지 않았다.
4. **OCR 재개는 같은 탭 안에서만 가능하다.** 지속적인 통신 오류는 유한 재시도 후 멈추고 완료한 페이지를 보관한다. 새로고침/종료에는 이탈 경고만 있으며 작업 복원 저장은 없다.
5. **교정 창을 열 때의 전체 OCR 초안 복사 비용은 남는다.** 입력 중 반복 순회는 줄였으나 매우 많은 인식 영역에서는 초안 생성 자체가 무거울 수 있다. 페이지별 지연 초안 생성이 후속 개선 대상이다.

단독 HTML은 두 로컬 OCR 엔진과 마스킹 엔진을 포함해 재생성했다. 이 환경의 브라우저 도구는 `file://` 접근을 제한하므로 파일을 더블클릭하는 실제 오프라인 실행과 물리 Android/iOS 기기 테스트는 이번 검증에 포함하지 않는다.
